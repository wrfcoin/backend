# Security Architecture Documentation

Historical configuration reference; this document is not evidence of current
public-testnet deployment or audit completion. For vulnerability reports, use
[the security policy](../SECURITY.md).

## Overview

This document outlines the security improvements implemented to address critical vulnerabilities
identified in the security audit. The new architecture eliminates private key exposure while
maintaining transaction integrity and user control.

## Security Improvements

### 1. Secure Wallet Service

**Problem:** Direct private key handling in API exposed keys to memory dumps and logs.

**Solution:** Implemented signature-based transaction validation using `SecureWalletService`.

#### Key Features:

- **No Private Key Storage:** API never stores or handles user private keys
- **Message Signing Verification:** Uses cryptographic signatures to verify transaction intent
- **Secure Admin Operations:** Admin wallet isolated with environment-based key management
- **Audit Trail:** Comprehensive logging of all security events

#### Transaction Flow:

1. User creates transaction request message
2. User signs message with their private wallet (client-side)
3. API verifies signature against expected message format
4. Admin wallet executes transaction on behalf of user (requires pre-approval)
5. All actions logged for security audit

### 2. Oracle Price Manipulation Protection

**Problem:** No validation of oracle price feeds could allow manipulation.

**Solution:** Implemented comprehensive oracle security with circuit breakers.

#### Security Mechanisms:

- **Price Deviation Checks:** Maximum 10% price change per validation
- **Staleness Validation:** Reject prices older than 1 hour
- **Confidence Scoring:** Minimum 80% oracle confidence required
- **Circuit Breakers:** Automatic protection when deviation exceeds 20%
- **Multi-Oracle Validation:** Fallback to AMM pricing when oracle fails

### 3. MEV/Front-Running Protection

**Problem:** Liquidation mechanism vulnerable to MEV extraction and front-running.

**Solution:** Implemented commit-reveal scheme with time delays and slippage protection.

#### Protection Features:

- **Commit-Reveal Scheme:** Two-step liquidation process prevents front-running
- **Time Delays:** 5-minute delay between commit and reveal phases
- **Liquidation Intervals:** Minimum 1-hour cooling period between liquidations
- **Slippage Protection:** Maximum price validation for liquidation execution
- **Batch Processing:** Efficient batch liquidation for authorized liquidators
- **Emergency Override:** Admin emergency liquidation capability

### 4. Flash Loan Authorization Fix

**Problem:** OR logic in authorization check allowed bypass with compromised admin key.

**Solution:** Changed to AND logic requiring both authorization and role validation.

#### Security Enhancement:

```solidity
// Before (vulnerable):
require(authorizedFlashBorrowers[msg.sender] || hasRole(DEFAULT_ADMIN_ROLE, msg.sender))

// After (secure):
require(authorizedFlashBorrowers[msg.sender] &&
        (hasRole(DEFAULT_ADMIN_ROLE, msg.sender) || hasRole(FACTORY_ROLE, msg.sender)))
```

## API Security Model

### Message Signing Protocol

#### 1. Transaction Request Message Format

```typescript
{
  contractAddress: string,
  functionName: string,
  params: any[],
  nonce: string,          // 32-byte random nonce
  expiry: number,         // Unix timestamp
  timestamp: number       // Request creation time
}
```

#### 2. Client-Side Signing Process

```javascript
// Client creates message
const message = {
  contractAddress: '0x...',
  functionName: 'retire',
  params: [tokenId, amount, reason, beneficiary],
  nonce: '0x...', // Generated by API
  expiry: 1640995200000, // 15 minutes from now
};

// User signs with their wallet
const signature = await wallet.signMessage(JSON.stringify(message));
```

#### 3. API Validation Process

```typescript
// Verify signature
const isValid = secureWalletService.verifyTransactionRequest(
  walletAddress,
  signature,
  contractAddress,
  functionName,
  params,
  nonce,
  expiry
);
```

### Admin Wallet Security

#### Environment Configuration

```bash
# Admin wallet for transaction execution (never exposed to API users)
ADMIN_PRIVATE_KEY=0x...

# Optional: Hardware Security Module integration
HSM_ENDPOINT=https://...
HSM_KEY_ID=...
```

#### Best Practices:

- Admin private key stored in secure environment variables
- Separate admin wallet for each environment (dev/staging/prod)
- Hardware Security Module (HSM) support for production
- Regular key rotation procedures
- Multi-signature admin wallets for critical operations

## Recovery Procedures

### Circuit Breaker Recovery

1. Oracle Manager role can reset individual token circuit breakers
2. Emergency role can toggle global circuit breaker
3. All resets logged with timestamps for audit

### Emergency Response

1. Emergency role can pause all contracts
2. Emergency liquidation bypasses MEV protection
3. Admin wallet can execute emergency withdrawals
4. All emergency actions logged and monitored

## Compliance and Auditing

### Audit Trail Requirements

- All transactions must have verifiable signatures
- Price updates logged with deviation calculations
- Liquidation attempts logged with timing data
- Security events archived for regulatory compliance

### Regular Security Reviews

- Monthly review of security logs
- Quarterly penetration testing
- Annual comprehensive security audit
- Continuous monitoring of oracle feeds and circuit breakers
